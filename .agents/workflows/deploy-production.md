# Production deployment

Как довести готовое изменение до `https://oftalmologia.pro`: локальные проверки →
коммит → push в GitHub → автоматический деплой на VPS → подтверждение результата.

Инфраструктурные факты не дублируются здесь: сервер, PM2, nginx, секреты, контракт
вызова `deploy.sh` и порядок отката описаны в
[`docs/architecture/PRODUCTION.md`](../../docs/architecture/PRODUCTION.md). При
расхождении верен он.

## Предусловия

1. Пользователь **явно** запросил production-действие. Push в `main` сам запускает
   деплой, поэтому отдельного «разрешения на деплой» после разрешения на push не
   существует — это одно и то же действие.
2. Запущен `project-infrastructure`, прочитан `PRODUCTION.md`. Заново исследовать
   сервер без признаков устаревшего runbook не нужно.
3. Для изменений схемы — `prisma-schema-safety`; разрешены только аддитивные
   операции.

## 1. Локальные проверки

Выполняются до коммита. Ни один шаг не пропускается.

```bash
npm run prisma:validate
npm test
npm run lint
npm run typecheck
NODE_OPTIONS='--max-old-space-size=1536' npm run build -- --webpack
```

Падение build на загрузке шрифтов Google (`Geist`) — сетевая проблема окружения, а
не кода: повторить при доступной сети и не выдавать за успех, если проверить не
удалось.

## 2. Коммит

Проверить состав перед staging:

```bash
git status
```

В репозиторий не попадают: `.vscode/`, локальные скриншоты и QR-файлы, временные
логи, любые ключи и токены. Добавлять файлы адресно, а не `git add -A`.

## 3. Push в репозиторий

Канонический remote — `https://github.com/Amd22002004/ophthalmology-encyclopedia.git`.
Серверный `deploy.sh` отказывается работать, если origin иной, поэтому форки и
зеркала не годятся.

Push должен идти от GitHub-пользователя **`Amd22002004`**. Учётные данные `vizus1`
дают `Permission denied` — это другой аккаунт, под которым проект когда-то
скаффолдился.

Две ловушки окружения на рабочей Windows-машине:

- **`git` не находится в PATH.** Запись в PATH содержит кириллическое имя
  пользователя и ломается на кодировке. Вызывать по полному пути:
  `& "$env:LOCALAPPDATA\Programs\Git\cmd\git.exe"`.
- **Агентская оболочка не может показать запрос пароля.** В ней выставлены
  `GIT_TERMINAL_PROMPT=0` и `GCM_INTERACTIVE=never`, поэтому credential manager не
  откроет окно браузера и push упадёт с `terminal prompts disabled`. Варианты:
  запушить с токеном, который предоставил оператор, либо попросить оператора
  выполнить push в своём интерактивном терминале.

Токен **никогда** не коммитится, не пишется в документацию и не попадает в
`AGENTS.md`. После использования его следует отозвать.

## 4. Деплой

Push в `main` автоматически запускает
[`.github/workflows/deploy.yml`](../../.github/workflows/deploy.yml). Для повторного
развёртывания уже существующего commit — `workflow_dispatch` с явным `ref`.

Полный цикл занимает около 4–5 минут: бэкапы, `git reset --hard`, `npm ci`,
Prisma generate, build, рестарт PM2, smoke-тесты.

Наблюдать за прогоном:
`https://github.com/Amd22002004/ophthalmology-encyclopedia/actions/workflows/deploy.yml`

Повторять упавший релиз «вслепую» нельзя: сначала прочитать лог job и выяснить
фактическое состояние production.

## 5. Подтверждение результата

Релиз завершён только когда:

- все шаги job зелёные, включая `Smoke-test the live site`;
- на сервере рабочая копия на ожидаемом commit, `node_modules` и `.next` на месте,
  PM2-процессы `ophthalmology-oftalmologia` и
  `ophthalmology-email-worker-oftalmologia` в статусе `online`;
- публичные маршруты отвечают `200`.

Отчитываться отдельно: что подтверждено локально, а что на production. Не
переносить локальный результат на production и наоборот.

## 6. Если деплой упал

1. Прочитать лог упавшего шага целиком, а не только последнюю строку.
2. Сверить симптом с разделом 10.1 `PRODUCTION.md` — там разобраны контракт вызова
   `deploy.sh`, требования к секретам и их характерные ошибки.
3. Если падение случилось **после** `git reset --hard` (на `npm ci` или build),
   production в хрупком состоянии: сайт жив только на уже запущенном процессе.
   Не перезапускать PM2 и не перезагружать сервер до восстановления зависимостей —
   см. 10.1.1 `PRODUCTION.md`.
4. Откат — по разделу 11 `PRODUCTION.md`, только при подтверждённой проблеме
   релиза. Откат БД требует отдельного подтверждения пользователя.

## 7. После релиза

Проверить необходимость обновить `PRODUCTION.md`, `ROADMAP.md` и `CHANGELOG.md`.
Для публичного изменения получить вывод `release-audit`.
