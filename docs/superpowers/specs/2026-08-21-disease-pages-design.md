# Полноценные страницы заболеваний: дизайн MVP

## Статус

Дизайн подтверждён пользователем 21 августа 2026 года. В MVP входят только
`/diseases/ambliopiya`, `/diseases/astigmatizm` и
`/diseases/vozrastnaya-makulyarnaya-degeneratsiya`.

## Цель

Превратить три существующие страницы `Disease` из минимальных карточек в
компактные медицинские справочники для пациентов, офтальмологов, поисковых
систем и AI-агентов, сохранив текущую модель графа, URL и визуальную систему.

Страница должна однозначно описывать сущность заболевания: название, синонимы,
категорию, определение, причины и факторы риска, симптомы, формы, диагностику,
лечение, наблюдение, связанные сущности и источники происхождения контента.

## Решение

### 1. Владелец данных и границы

`Disease` остаётся владельцем идентичности и графовых связей в Prisma:
`slug`, `title`, категория, врачи, процедуры, клиники, публикации, научные
работы, клинические рекомендации и расследования.

Prisma schema не изменяется. Отдельная сущность `DiseaseContent` в базе не
создаётся: для трёх статических редакционных материалов используется
типизированный content registry в `src/lib/disease-content.ts`. Registry не
дублирует существующие связи и факты БД; он владеет структурой статьи, SEO,
изображением, FAQ и provenance медицинского текста.

Для будущего заболевания добавляется ещё одна запись в registry, а шаблон и
loader не меняются. Пустые или не вошедшие в MVP заболевания продолжают
рендериться текущим минимальным fallback-шаблоном.

### 2. Контракт `DiseaseContent`

Каждая запись содержит:

- `slug`, `summary`, `aliases`, `seo.title`, `seo.description`;
- `image.src`, `image.alt`, `image.width`, `image.height`;
- справочные секции: `definition`, `causes`, `riskFactors`, `symptoms`,
  `types`, `diagnosis`, `treatment`, `prognosis`, `prevention`,
  `whenToSeeDoctor`;
- конкретные списки диагностических и лечебных методов, только если они
  медицински уместны;
- `faq` минимум из 7 вопросов с полноценными ответами;
- `relatedDiseaseSlugs` только для существующих страниц;
- `sources[]` с `name`, `url`, `accessedAt`, опциональной датой обновления
  источника и массивом `sections`, на которые он опирается.

Разделы представлены структурированными абзацами/списками, а не одной длинной
строкой. Неуместный раздел остаётся пустым и не рендерится. Редакционные ссылки
между заболеваниями являются навигационными ссылками контента, а не новой
Prisma-связью `Disease ↔ Disease`.

### 3. Loader и граф

`getDisease(slug)` продолжает получать фактическую сущность и прямые связи из
Prisma, добавляя только registry-контент и проверенные существующие
`relatedDiseaseSlugs`. Для разрешения связанных заболеваний loader выбирает
только строки с реально найденным slug; несуществующие ссылки отбрасываются.

Loader не выводит клиники через врачей. Блок «Клиники» появляется только при
прямых строках `ClinicOnDisease`. Нормативные материалы не добавляются:
текущая модель не содержит прямой `Disease ↔ Regulation` связи, а клинические
рекомендации выводятся только через `DiseaseOnClinicalGuideline`.

Для MVP добавляются только две прямые связи, подтверждённые медицинскими
источниками и уже существующими страницами процедур:

- `astigmatizm → lazernaya-korrektsiya-zreniya`;
- `vozrastnaya-makulyarnaya-degeneratsiya → anti-vegf-terapiya`.

Для амблиопии существующие страницы процедур не выражают подходящие методы
окклюзии/пенализации, поэтому эти методы описываются текстом без искусственной
ссылки на неподходящую процедуру.

### 4. Единый шаблон

Текущий `DiseaseTemplate` становится универсальным: при наличии `content`
рендерится rich-вариант, иначе сохраняется текущая fallback-ветка.

Rich-вариант состоит из:

1. кликабельных breadcrumbs: `Главная → Заболевания → [название]`;
2. компактного hero в стиле `EntityHeader`: один H1, категория, краткое
   определение и уникальная медицинская иллюстрация справа;
3. основной колонки статьи с реальными `h2` и карточками `Card`/`EntityBlock`;
4. отдельного заметного блока «Когда необходима очная диагностика»;
5. FAQ на нативных доступных `details/summary` без обязательной клиентской
   гидратации;
6. sidebar с прямыми связями врачей, процедур, публикаций, научных работ,
   клинических рекомендаций, оборудования и расследований — только если они
   существуют;
7. блоков связанных заболеваний и источников.

Главный текст не помещается в sidebar. На мобильной ширине колонки становятся
последовательными, длинные названия переносятся, изображения имеют стабильные
размеры.

### 5. SEO и Schema.org

`generateMetadata` использует уникальные title/description из registry,
канонический путь `/diseases/[slug]`, `robots: index, follow`, OpenGraph с
изображением и размеры/alt изображения. Для rich-страниц title задаётся как
абсолютный, чтобы не получить двойной суффикс из root title template.

В HTML-LD добавляются только подтверждённые сущности:

- `MedicalWebPage` для страницы справочника;
- `BreadcrumbList` с теми же кликабельными URL;
- `MedicalCondition` с названием, описанием, синонимами, категорией и МКБ,
  если код присутствует;
- `FAQPage` только при наличии видимого FAQ.

Свойства без фактических данных не создаются. Внутренние ссылки используют
только существующие маршруты и прямые связи/явно обозначенные редакционные
ссылки.

### 6. Изображения

После подтверждения дизайна создаются три разные raster-иллюстрации через
imagegen и сохраняются в проекте:

- `public/images/diseases/ambliopiya.webp`;
- `public/images/diseases/astigmatizm.webp`;
- `public/images/diseases/vozrastnaya-makulyarnaya-degeneratsiya.webp`.

Иллюстрации не содержат текста, логотипов, водяных знаков и рекламных элементов.
Hero-изображение находится above-the-fold, получает `width`/`height` и
`preload`; ниже первого экрана изображения, если появятся в будущем, будут
лениво загружаться.

### 7. Источники и редакционная политика

Медицинский текст опирается на National Eye Institute и AAO EyeWiki. В каждой
записи registry сохраняется provenance по разделам, чтобы редактор мог увидеть,
какой источник поддерживает определение, симптомы, диагностику или лечение.
Текст остаётся кратким справочным материалом без SEO-повторов, назначения
самолечения, обещаний результата и рекламных формулировок.

## Проверки готовности

- автоматические тесты контракта registry: три slug, уникальные SEO-поля,
  корректные assets, FAQ не менее 7 вопросов и provenance каждого раздела;
- тесты Schema.org/metadata и отсутствие фальшивых ссылок в контентных refs;
- `npm test`, `npm run lint`, `npm run typecheck`, `npm run prisma:validate`,
  `npm run build`;
- локальный production smoke test трёх URL с HTTP 200, canonical, robots,
  OpenGraph, JSON-LD, одним H1, FAQ и отсутствием 404 внутренних ссылок;
- браузерный UI-аудит desktop и 375–390 px;
- проверка, что остальные заболевания не получили rich-контент;
- documentation maintenance и release-audit до решения о публикации.

Production-деплой в этот этап не входит.
