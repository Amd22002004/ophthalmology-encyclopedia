# UI guidelines

> Статус: SSOT по интерфейсной философии проекта.
> Этот документ описывает визуальные правила, а не API React-компонентов.
> Фактические компоненты находятся в `src/components/`.

## 1. Философия интерфейса

Интерфейс энциклопедии должен выглядеть как профессиональная медицинская база
знаний: спокойный, доказательный, компактный и пригодный для повторного чтения.

Главные принципы:

- не превращать страницы в маркетинговые лендинги;
- не добавлять декоративные элементы без информационной функции;
- показывать связи и доказательства явно;
- сохранять одинаковое поведение карточек одного типа;
- не создавать отдельный стиль под одну сущность или расследование.

## 2. Design System

Канонические токены заданы в `src/app/globals.css`.

| Роль | Значение |
| --- | --- |
| Фон страницы | `--background: #f7faf9` |
| Основной текст | `--foreground: #14211f` |
| Карточка | `--card: #ffffff` |
| Primary | `--primary: #0f766e` |
| Muted | `--muted: #eef4f3` |
| Border/Input | `--border`, `--input: #d8e3e1` |
| Destructive | `--destructive: #b42318` |
| Radius | `--radius: 0.5rem` |

Новые UI-решения должны использовать эти токены, существующие `Card`, `Button`,
`EntityBlock`, `RelatedBlock`, `TemplateShell`, `InvestigationNotice` и локальные
паттерны. Не вводить вторую палитру и не строить отдельную Design System.

## 3. Карточки

Базовая карточка:

- белый фон;
- тонкая граница;
- `rounded-lg`;
- лёгкая тень только для отделения от фона;
- внутренний отступ обычно `p-5`;
- заголовок `text-base font-semibold`;
- описание `text-sm text-muted-foreground`.

Повторяемые карточки в каталоге должны иметь сопоставимую высоту. Если у сущности
есть статус, предупреждение или расследование, этот статус выводится отдельным
связанным блоком, но не ломает внутренний шаблон карточки.

## 4. Сетка страниц

Каталоги:

- фильтры отдельной компактной карточкой над списком;
- сетка карточек `sm:grid-cols-2`, `xl:grid-cols-3`;
- gap обычно `4`;
- пустое состояние показывается одной спокойной карточкой, без декоративного hero.

Страницы сущностей:

- верхний `TemplateShell`: breadcrumbs, eyebrow, title, description, badges;
- основной контент и sidebar на широких экранах;
- типовая сетка detail-страниц: `xl:grid-cols-[minmax(0,1fr)_300px]` или близкая;
- sidebar используется для связей, реквизитов, карты, документов и вторичных блоков;
- пустые разделы не рендерятся.

## 5. Отступы и плотность

Проект использует плотный, но читаемый медицинский интерфейс:

- между крупными блоками: `space-y-5` или `gap-5`;
- внутри карточек: `p-4` / `p-5`;
- компактные списки связей: `space-y-2`;
- большие вертикальные пустоты допустимы только между смысловыми разделами статьи.

Не использовать избыточные hero-отступы, крупные декоративные секции и вложенные
карточки там, где достаточно блока с границей.

## 6. Типографика

Базовый шрифт: Geist Sans через Next.js.

Правила:

- H1 задаётся шаблоном сущности;
- заголовки карточек короткие и плотные;
- текст статьи: 14-15 px, `leading-6` или `leading-7`;
- технические подписи: 11-12 px, uppercase допустим только для меток;
- длинные медицинские названия не должны обрезаться без причины;
- `font-mono` использовать только для реквизитов, ИНН, ОГРН и технических значений.

## 7. Цвет

Основной смысловой цвет — зелёный primary. Он используется для:

- ссылок;
- акцентов в списках;
- активных фильтров;
- медицинских и энциклопедических статусов.

Жёлтый/amber используется только для предупреждений и расследований, где нужен
нейтральный сигнал внимания. Красный используется осторожно: для destructive-смысла
или связи карточки с активным расследованием, но не как общий фон карточки.

## 8. Предупреждения

`InvestigationNotice` — канонический паттерн предупреждений расследования.

В каталоге клиник:

- компактный alert высотой около 40-50 px;
- светло-жёлтый фон;
- тонкая оранжевая граница;
- одна строка: «Проводится проверка использования оборудования.»;
- alert визуально соединён с карточкой;
- карточка получает красную рамку/лёгкое свечение;
- внутрь карточки не добавляются новые тексты расследования.

На странице клиники:

- предупреждение располагается над информацией о клинике;
- можно использовать более развёрнутый текст;
- обязательно должна быть ссылка на расследование.

Для оборудования:

- использовать нейтральный информационный стиль;
- не применять красный предупреждающий тон, если оборудование только упоминается
  в расследовании.

## 9. Расследования

Расследование — доказательный материал, а не обычная статья.

UI должен показывать:

- статус расследования;
- хронологию;
- разделы материала;
- документы как встроенную доказательную базу;
- связанные клиники, оборудование, процедуры, заболевания и новости.

Документы не прятать за одной ссылкой. Для каждого документа показывать публичное
название, описание, дату и источник. Не показывать внутренние имена файлов,
служебные markdown-файлы и названия генераторов изображений.

## 10. Карточки клиник

Каталожная карточка клиники сохраняет стандартный вид:

- логотип/инициал;
- название;
- бейджи ОМС, сеть, тип;
- адрес;
- специализации или «Профиль уточняется»;
- лицензия;
- телефон и ссылка «Профиль».

Нельзя менять внутренний шаблон карточки ради одного статуса. Расследование в
каталоге отображается внешним alert и рамкой контейнера.

Страница клиники может быть богаче: header, CTA, врачи, оборудование, реквизиты,
карта, связанные процедуры и заболевания.

## 11. Оборудование

Карточка оборудования — энциклопедическая статья с технической структурой.

Эталонный состав:

- hero с основным изображением;
- краткие факты: производитель, страна, категория, год, поставщик;
- описание;
- история модели;
- эволюция модели;
- таймлайн;
- принцип работы;
- преимущества, показания, ограничения;
- техническая таблица;
- галерея;
- документы;
- видео, если источник официальный;
- сравнение;
- FAQ;
- sidebar со связанными клиниками, процедурами, заболеваниями, врачами, новостями.

Технические характеристики показывать таблицей, а не произвольным списком.
Изображения должны иметь стабильный aspect-ratio, чтобы не создавать CLS.

## 12. Новости

Новость оформляется как редакционная входная точка:

- основной текст в статье;
- sidebar с опубликованными документами и связанными сущностями;
- блок перехода к полному расследованию, если новость связана с ним.

Новость не должна визуально конкурировать с расследованием и не должна заменять
доказательную карточку расследования.

## 13. Hero-блоки

Hero допустим только когда он помогает идентифицировать сущность. Для энциклопедии
это чаще `EntityHeader`, а не маркетинговый полноэкранный блок.

Не использовать:

- крупные декоративные hero без данных;
- градиентные заставки;
- иллюстрации ради иллюстраций;
- hero, который скрывает первый полезный раздел ниже первого экрана.

## 14. Sidebar

Sidebar применять для вторичной, но важной информации:

- связанные сущности;
- документы;
- реквизиты;
- карта;
- новости по связанному расследованию;
- навигационные блоки.

Не помещать в sidebar главный текст страницы. На мобильной ширине sidebar должен
становиться обычным последовательным блоком.

## 15. Документы

Карточка документа должна показывать:

- публичное название;
- тип или роль документа;
- краткое описание;
- дату, если есть;
- источник, если есть;
- кнопку или ссылку открытия.

Запрещено показывать:

- внутренний путь;
- исходное имя файла;
- временное имя;
- имя генератора изображения;
- markdown-файл как публичный документ.

## 16. Связанные материалы

Связанные сущности оформляются компактными ссылками с заголовком и optional meta.
Если связей нет, блок не рендерится, кроме случаев, когда пустое состояние помогает
пользователю понять результат фильтра.

Ссылка должна вести на сущность, которая реально существует и связана по смыслу.

## 17. Адаптивность

Минимальные требования:

- каталоги читаются на 375-390 px без горизонтального скролла;
- длинные названия переносятся;
- кнопки не сжимают текст до нечитаемого состояния;
- таблицы допускают горизонтальный scroll только внутри своего контейнера;
- изображения имеют заданный aspect-ratio или стабильные размеры;
- alert в каталоге не ломает высоту карточки и не становится отдельной ячейкой.

## 18. Визуальная иерархия

Перед сдачей UI спросить:

1. Пользователь сразу понимает, что это за сущность?
2. Главный следующий шаг виден без поиска?
3. Доказательства и связи отделены от описательного текста?
4. Добавленный блок действительно улучшает понимание?
5. Решение сохраняет стиль проекта без нового визуального языка?

Если ответ отрицательный, упрощать интерфейс и возвращаться к существующим паттернам.

## 19. Обращения

Форма обращения — самостоятельный последовательный сценарий, а не карточка
оборудования и не всплывающее окно. Использовать стандартные `EntityHeader`, `Card`,
`Input`, `Button`, спокойные границы и существующую типографику.

- CTA допустим на странице расследования, новости и в разделе независимого контроля;
- форма находится только на `/appeal` и принимает контекст расследования;
- `/contact` не имеет отдельного интерфейса и используется только как постоянный
  redirect на каноническую форму;
- FAQ не содержит форму: в конце страницы или статьи используется компактный CTA;
- длинные группы полей делятся на смысловые карточки;
- юридическая конфигурация показывается целиком в прокручиваемом контейнере;
- признак неутверждённого шаблона оформляется нейтральным amber-alert;
- успешная отправка заменяет форму подтверждением и публичным номером;
- персональные данные и исходные имена файлов не появляются в публичном UI;
- админ-таблица допускает горизонтальный scroll внутри контейнера, а карточка
  обращения сохраняет читаемую двухколоночную композицию на широком экране.

На странице расследования основной CTA после доказательств остаётся главным.
Компактный fixed CTA разрешён только после ухода основного блока выше viewport:

- desktop: справа по центру, ширина около 240 px;
- mobile: снизу, около 90% ширины, с учётом `safe-area-inset-bottom`;
- z-index ниже шапки, диалогов и внешних системных баннеров;
- видимость определяется `IntersectionObserver`, не `scroll`-обработчиком;
- перед итоговым CTA в потоке fixed-блок скрывается и не перекрывает конец страницы;
- допустимо только медленное scale-дыхание `1 → 1.03 → 1` за 5–6 секунд;
- при `prefers-reduced-motion` дыхание и переходы отключаются;
- нижний отступ резервируется CSS-переменной `--floating-ui-bottom-offset`, чтобы
  cookie-banner или чат могли увеличить его без изменения компонента.

## 20. Нормативная база и оценки расследования

Карточка `/regulations/[slug]` должна выглядеть как рабочий юридический справочник,
а не как лента претензий. В первом экране показывать акт, номер, орган, правовой
статус, период действия и кликабельный официальный источник. Ниже — редакции,
атомарные положения, check questions и виды первичных документов.

- длинные таблицы стандартов оснащения прокручиваются только внутри контейнера;
- текущая, будущая и утратившая силу редакции различаются текстом и спокойными
  badge, а не одним цветом;
- официальный источник открывается как обычная доступная ссылка с понятной подписью;
- скрытое положение, вопрос или источник не должен оставлять пустую оболочку;
- клиники, серийные номера, реестровые результаты и ссылки на расследования на
  нормативной карточке не выводятся.

В `Investigation` нормативный блок может показывать конкретный экземпляр, период,
применённую редакцию, первичные документы, обе доказательные версии, пробелы и один
из пяти фиксированных статусов — только после publication gate соответствующих
узлов. Модель оборудования всегда отделяется от экземпляра визуальной подписью.

Статусы не кодируются обвинительной палитрой: красный не используется как
автоматический эквивалент нарушения. Текст статуса и основание должны оставаться
понятными без цвета. `REQUIRES_VERIFICATION` оформляется как нейтральная
неопределённость, а `NO_MATCH` — как результат конкретного поиска, не итоговая
оценка.
