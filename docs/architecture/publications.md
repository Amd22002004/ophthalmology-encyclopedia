# Публикации: `ScientificWork` vs `Publication`

> Статус: **v1, заморожено**. Сверено с `prisma/schema.prisma`.

## 1. Главное в одном абзаце

Это **две разные сущности**, живущие в одном разделе `/publications`.
`ScientificWork` — научная работа конкретного врача (диссертация, патент, статья).
`Publication` — редакционный материал энциклопедии (статья журнала, обзор).
Данные между ними **не дублируются**: у каждой работы ровно один владелец-таблица.

## 2. Почему это разные сущности

| | `ScientificWork` | `Publication` |
|---|---|---|
| **Природа** | Научная деятельность врача | Редакционный контент |
| **Автор** | `doctorId` — **обязателен** (NOT NULL) | `doctorId` — **необязателен**; либо `authorName` строкой |
| **Существует без врача?** | Нет. Удаление врача → `Cascade` | Да. Удаление врача → `SetNull`, материал живёт |
| **Специфика** | Учёная степень, специальность ВАК, место защиты, научный руководитель, новизна, практическая значимость, результаты | Тип публикации, дата, аннотация, полный текст |
| **Полный текст** | В БД **не хранится** — только PDF-файл | Хранится в `content` |
| **Ключевой смысл** | Подтверждение экспертизы врача | Информационный материал |

Слить их в одну модель нельзя: у `ScientificWork` автор — обязательный владелец
(работа не существует в отрыве от врача), у `Publication` — опциональный атрибут.
Это противоположные инварианты. Попытка объединения дала бы модель, где половина полей
всегда пустая, а инвариант «у работы есть автор» перестал бы соблюдаться на уровне БД.

## 3. Когда что использовать

| Материал | Сущность |
|---|---|
| Кандидатская / докторская диссертация | `ScientificWork` |
| Автореферат | `ScientificWork` |
| Патент, свидетельство на рацпредложение | `ScientificWork` |
| Методические рекомендации, монография | `ScientificWork` |
| Научная статья врача проекта | `ScientificWork` |
| Обзорная статья энциклопедии | `Publication` |
| Материал журнала, редакционный текст | `Publication` |
| Статья внешнего автора (нет в системе врачей) | `Publication` (`authorName`) |

**Правило:** если у материала есть врач-автор **из системы** и материал подтверждает
его научную квалификацию — это `ScientificWork`. Всё остальное — `Publication`.

## 4. Почему данные не дублируются

1. **У факта один владелец (SSOT).** Диссертация Островерхова живёт **только** в
   `ScientificWork`. Копии в `Publication` нет и быть не должно.
2. **Каталог не копирует, а читает.** `/publications` строится запросом к
   `ScientificWork` напрямую — витрины/копии данных нет.
3. **Единый тип отображения.** Загрузчик приводит обе сущности к общему
   `PublicationCatalogItem` с полем-дискриминатором `kind`:

```ts
type PublicationCatalogItem = {
  kind: "scientific" | "editorial";
  slug: string;
  type: string;
  title: string;
  authorName: string;
  authorSlug: string | null;
  year: number | null;
  organization: string | null;
  diseases: { slug: string; title: string }[];
  procedures: { slug: string; title: string }[];
};
```

Это **тип отображения**, а не таблица. Он не хранится в БД и ничего не дублирует.

## 5. Структура `ScientificWork`

| Поле | Тип | Назначение |
|---|---|---|
| `id` | `String` | PK |
| `slug` | `String?` @unique | URL `/publications/[slug]`. Nullable — см. §5.1 |
| `doctorId` | `String` | FK → `Doctor`, **NOT NULL**, `Cascade` |
| `type` | `String` | «Кандидатская диссертация», «Патент», … |
| `title` | `String` | Название работы |
| `degree` | `String?` | Учёная степень |
| `speciality` | `String?` | Специальность ВАК |
| `year` | `Int?` | Год защиты |
| `organization` | `String?` | Место защиты |
| `supervisor` | `String?` | Научный руководитель («ФИО, степень, звание») |
| `summary` | `String?` | Аннотация простым языком (3–5 предложений) |
| `novelty` | `String[]` | Научная новизна |
| `practicalValue` | `String[]` | Практическая значимость |
| `results` | `String[]` | Основные результаты |
| `publicationCount` | `Int?` | Число публикаций по теме |
| `pdfUrl` | `String?` | Полный текст (PDF) |
| `abstractUrl` | `String?` | Автореферат (PDF) |
| `sortOrder` | `Int` = 0 | Порядок у врача |

Ограничения: `@@unique([doctorId, title])`, `@@unique(slug)`,
`@@index([doctorId, sortOrder])`, `@@index([year])`.

### 5.1 Почему `slug` nullable

Технически вынужденно. Колонка добавлялась к **непустой** таблице; `NOT NULL` без
значения по умолчанию потребовал бы деструктивной миграции (пересоздание таблицы),
а `@default` несовместим с `@unique` при нескольких строках.

Компенсация:
- seed **всегда** проставляет `slug`;
- каталог фильтрует `where: { slug: { not: null } }`;
- счётчик на главной считает только работы со `slug`.

Работа без `slug` в каталог не попадёт — это осознанный контракт, а не баг.

### 5.2 Полный текст в БД не хранится

В БД — только структурированные данные. Диссертация и автореферат отдаются
**файлами** из `public/doctors/<doctor-slug>/`. Причина: БД — не файловое хранилище;
полный текст диссертации (сотни страниц) не нужен ни для поиска, ни для отображения.

## 6. Структура `Publication`

| Поле | Тип | Назначение |
|---|---|---|
| `id` | `String` | PK |
| `slug` | `String` @unique | URL `/publications/[slug]` |
| `title` | `String` | Заголовок |
| `publicationType` | `String?` | Тип материала |
| `publishedAt` | `DateTime?` | Дата публикации |
| `authorName` | `String?` | Автор строкой (внешний) |
| `abstract` | `String?` | Аннотация |
| `content` | `String?` | Полный текст |
| `doctorId` | `String?` | FK → `Doctor`, nullable, `SetNull` |

## 7. Связи

```
ScientificWork                      Publication
 ├─→ Doctor      (прямая, NOT NULL)  ├─→ Doctor      (прямая, nullable)
 ├─→ Diseases    (прямая)            ├─→ Diseases    (прямая)
 ├─→ Procedures  (прямая)            ├─→ Procedures  (прямая)
 └─→ Clinics     (ВЫЧИСЛЯЕМАЯ)       └─→ Clinics     (прямая, ClinicOnPublication)
```

| Связь | Таблица |
|---|---|
| `ScientificWork ↔ Disease` | `ScientificWorkOnDisease` |
| `ScientificWork ↔ Procedure` | `ScientificWorkOnProcedure` |
| `Publication ↔ Disease` | `PublicationOnDisease` |
| `Publication ↔ Procedure` | `PublicationOnProcedure` |
| `Publication ↔ Clinic` | `ClinicOnPublication` |

**Ключевое правило:** заболевания и процедуры научной работы — **только прямые связи**
(тема работы), никогда не через врача. Обоснование с реальным примером —
[`graph-model.md`](./graph-model.md) §4.2.

## 8. Как строится каталог `/publications`

1. `getPublicationsCatalog()` читает `ScientificWork` (`where: slug != null`),
   сортировка `year DESC`, затем `sortOrder ASC`.
2. Каждая запись приводится к `PublicationCatalogItem` с `kind: "scientific"`.
3. Структура готова принять `Publication` (`kind: "editorial"`) в тот же каталог —
   типы контента будут различаться бейджем, но не смешиваться семантически.

**Автоматизм:** новая научная работа врача появляется в каталоге **без единой строки
кода** — каталог читает таблицу напрямую. Проверено: добавление работы другому врачу
сразу дало карточку в каталоге, рабочую страницу и запись на странице заболевания.

Карточка каталога: тип работы · бейдж типа контента · название · автор (ссылка) · год ·
организация · заболевания (пилюли) · процедуры (пилюли) · «Подробнее →».

## 9. Как строится страница `/publications/[slug]`

Маршрут обслуживает **оба** типа контента:

1. Ищем `ScientificWork` по `slug` → рендерим `ScientificWorkTemplate`.
2. Не нашли → ищем `Publication` по `slug` → `PublicationTemplate`.
3. Не нашли → `notFound()`.

Состав страницы научной работы: шапка (тип · год · ВАК) → «О работе» (Автор / Тема /
Место защиты / Научный руководитель / Специальность ВАК / Публикации) → Аннотация →
Научная новизна → Практическая значимость → Основные результаты (метрики) →
Документы исследования.
Сайдбар: Автор · Заболевания в исследовании · Методики в исследовании · **Клиники автора**.

### 9.1 Общий UI со страницей врача

Компоненты вынесены в `src/components/entity/scientific-work-ui.tsx`
(`InfoField`, `NoveltyCard`, `PracticalCard`, `ResultCard`, `DocCard`, парсеры).
Их используют **и** блок «Научная деятельность» на странице врача, **и** страница работы.

**Не дублировать эти компоненты локально** — иначе оформление разделов разойдётся.

### 9.2 Метрики результатов

`ResultCard` извлекает из текста результата ведущий числовой показатель
(`46,0 %`, `35,2 мкм`, `95,6 %`) и показывает его крупно, полный текст — под ним.
Значение берётся **дословно из строки**; если показателя нет — карточка выводит
только текст. Ничего не досчитывается и не додумывается.

## 10. Счётчик публикаций

`getEntityCounts()` возвращает `publications = Publication.count() + ScientificWork.count({ slug != null })`.
Считать только `Publication` нельзя — она пуста, и раздел показывал бы `0`
при непустом каталоге.

## 11. SEO

- Canonical `/publications/[slug]`.
- Schema.org научной работы: `ScholarlyArticle` (`headline`, `author` → `Person` со
  ссылкой на врача, `abstract`, `datePublished`, `publisher`) + `BreadcrumbList`.
- Заголовки разделов — реальные heading-теги.
