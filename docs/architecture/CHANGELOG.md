## v1 — 2026-07-15

**Статус: модель данных заморожена.**

Первая полная версия архитектуры энциклопедии. Сформирован граф знаний, зафиксирована
модель данных, создана архитектурная документация.

### Добавлены сущности

| Сущность | Роль в графе |
|---|---|
| `Doctor` | Врач — центральный узел: клиники, заболевания, процедуры, оборудование, работы |
| `Clinic` | Клиника — врачи, оборудование, специализации, юр. данные |
| `Disease` | Заболевание |
| `Procedure` | Процедура / методика |
| `Equipment` | Оборудование |
| `EquipmentSpec` | Характеристика оборудования (группа/параметр/значение) |
| `ScientificWork` | Научная работа врача |
| `Publication` | Редакционный материал |
| `Supplier` | Поставщик оборудования |
| **Graph Knowledge Model** | 20 связующих таблиц, двусторонняя перелинковка |

Полный состав (39 моделей, включая справочники и служебные) — [`overview.md`](./overview.md) §2.

### Реализовано

- **Каталог врачей** — карточки, страница врача, связи с клиниками и энциклопедией
- **Каталог клиник** — фильтры, страница, блоки врачей и оборудования
- **Каталог оборудования** — страница с ТХ, галереей, документами и связями
- **Каталог публикаций** — строится из `ScientificWork` автоматически
- **Научная деятельность врача** — блок на странице врача + страница работы
- **`ScientificWork`** — научная работа как полноценная сущность со своим `slug`
- **`EquipmentSpec`** — характеристики любого прибора без изменения схемы
- **SEO-перелинковка** — canonical, OpenGraph, Schema.org, sitemap
- **Идемпотентный seed** — повторный прогон не создаёт дублей

## Замороженные модели

Изменение допускается **только после отдельного архитектурного решения**
с одновременным обновлением документации.

| Модель | Статус | Документ |
|---|---|---|
| **`Equipment`** (+ `EquipmentSpec`) | 🔒 **Заморожена** | [`equipment.md`](./equipment.md) |
| **`ScientificWork`** | 🔒 **Заморожена** | [`publications.md`](./publications.md) |
| **Graph Knowledge Model** | 🔒 **Базовая архитектура проекта** | [`graph-model.md`](./graph-model.md) |

### Что разрешено при замороженной модели

✅ Добавлять записи · связи · характеристики · фотографии · PDF · менять UI.

### Что запрещено

❌ Менять существующие поля · создавать альтернативные модели для покрытой области ·
менять семантику связей · менять структуру без архитектурного решения.

### Почему заморожены именно эти

- **`Equipment`** — масштабируемость подтверждена эмпирически: 8 разнотипных аппаратов
  (лазеры, ОКТ, биометры, микроскопы, витреосистемы) добавляются **только данными**.
  Ключ — `EquipmentCategory` + `EquipmentSpec` вместо колонок под каждый прибор.
- **`ScientificWork`** — покрывает диссертации, авторефераты, патенты, статьи,
  методические рекомендации, монографии. Тип работы — строка `type`, а не подмодель.
- **Graph Knowledge Model** — от неё зависят все страницы и вся перелинковка;
  изменение семантики связи ломает достоверность энциклопедии.

## Архитектурные решения v1

Полное изложение — [`design-principles.md`](./design-principles.md).

| Принцип | Суть |
|---|---|
| **Entity First** | Значимая единица знания — сущность со `slug` и страницей, а не поле или текст |
| **Graph Knowledge** | Ценность — в связях; каждая сущность встроена в граф, связи двусторонние |
| **SSOT** | У факта ровно один владелец; каталог читает таблицу, а не хранит копию |
| **Отказ от дублирования данных** | Никаких копий записей между таблицами и производных значений |
| **Только достоверные связи** | Нет источника — нет связи. Пустой раздел лучше выдумки |
| **Прямые связи предпочтительнее транзитивных** | Транзитивность — только если утверждение истинно по построению |
| **Расширение вместо дубликатов** | Сначала данные, потом связь, потом аддитивное поле; новая сущность — в последнюю очередь |
| **Аддитивность миграций** | Только `ADD COLUMN` (nullable) / `CREATE TABLE` / `CREATE INDEX`. Никаких `DROP` / `ALTER COLUMN` / `RENAME` |

### Ключевые решения, принятые в v1

**1. Связи научной работы — прямые, не через врача.**
Транзитивный вывод дал бы ложные медицинские связи: диссертация про кросслинкинг
попала бы на страницы «Катаракта» и «Птоз» (направления автора ≠ тема работы).
Созданы `ScientificWorkOnDisease` и `ScientificWorkOnProcedure`.
→ [`graph-model.md`](./graph-model.md) §4.2

**2. Клиники научной работы — через автора, без своей таблицы.**
`ScientificWorkOnClinic` **не создаётся**: факт уже выражен цепочкой
`work.doctor → DoctorOnClinic`. Здесь транзитивность корректна («клиники автора»).

**3. `Equipment → ScientificWork` не создаётся.**
Разные предметные области. Для исследований аппарата предусмотрена будущая сущность
`ClinicalStudy`, а не переиспользование `ScientificWork`.

**4. `Publication` и `ScientificWork` — разные сущности.**
У `ScientificWork` автор обязателен (владелец), у `Publication` — опционален.
Противоположные инварианты; объединение сломало бы гарантию «у работы есть автор».
Оба типа живут в одном каталоге `/publications`, различаясь полем `kind` **в типе
отображения**, а не в БД.
→ [`publications.md`](./publications.md)

**5. `EquipmentSpec` вместо колонок и `Json`.**
Характеристики приборов разных классов несопоставимы. Колонки росли бы под каждый
аппарат, `Json` непрозрачен. `group/label/value` — универсально и заморозило модель.

**6. Сущности `Organization` не существует.**
Её роли закрыты: `Supplier`, `Clinic` (юр. поля), `ScientificWork.organization`,
`Equipment.manufacturer`. Единый справочник юрлиц — отдельное решение.
→ [`overview.md`](./overview.md) §2.6

## Правила обновления

После каждого завершённого крупного этапа необходимо обновить:

1. **`ROADMAP.md`** — перенести задачу между блоками (⬜ → 🟡 → ✅), обновить фактические
   цифры наполнения.
2. **`CHANGELOG.md`** — добавить новую версию с описанием архитектурных изменений.

**Обязательно при изменении модели данных:**

3. Обновить профильный документ (`doctors.md`, `equipment.md`, …).
4. Обновить [`graph-model.md`](./graph-model.md), если появились/изменились связи —
   с указанием типа: прямая / вычисляемая / намеренно отсутствует.
5. Обновить [`overview.md`](./overview.md), если появилась новая сущность.

> Эти документы — **часть архитектуры проекта**, а не сопроводительный текст.
> Они являются источником истины наравне с `prisma/schema.prisma` и должны
> поддерживаться в актуальном состоянии. Изменение архитектуры без обновления
> документации считается незавершённым.
