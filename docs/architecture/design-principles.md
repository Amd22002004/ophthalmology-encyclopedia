# Принципы проектирования энциклопедии

> Статус: **v1, заморожено**. Обязательны к соблюдению при любом изменении проекта.

## 1. Entity First Architecture

Каждая значимая единица знания — **самостоятельная сущность** со своим `slug`,
страницей и местом в графе. Не атрибут другой сущности и не строка текста.

**Практика:**
- Диссертация — не текстовое поле у врача, а `ScientificWork` со страницей
  `/publications/[slug]`.
- Характеристика прибора — не колонка, а строка `EquipmentSpec`.

**Проверка:** если на сущность нельзя сослаться ссылкой — она не встроена в граф.

## 2. Graph Knowledge Model

Ценность энциклопедии — в связях, а не в объёме отдельных страниц.

**Правила:**
1. **Двусторонность.** Если A ссылается на B, страница B показывает A.
2. **Связь именуется по смыслу.** «Заболевания в исследовании» и «Основные направления»
   ведут на `Disease`, но это разные утверждения и разные связи.
3. **Новая сущность обязана встроиться в граф.** Изолированная сущность бесполезна.
4. **Пустые блоки не рендерятся.** Отсутствие связей — не повод показывать пустоту.

## 3. SSOT — Single Source of Truth

У каждого факта **ровно один владелец**.

**Практика:**
- Диссертация хранится только в `ScientificWork`. Копии в `Publication` нет.
- Каталог `/publications` **читает** таблицу, а не хранит витрину.
- Полный текст диссертации — в PDF-файле, не в БД.
- Технические характеристики — только в `EquipmentSpec`.

**Проверка:** если факт нужно изменить в двух местах — SSOT нарушен.

## 4. Никакого дублирования данных

**Запрещено:**
- копировать записи между таблицами ради удобства выборки;
- заводить вторую модель для уже покрытой области (второй «оборудование»);
- хранить производные значения, которые вычисляются из связей.

**Тип отображения ≠ дублирование.** `PublicationCatalogItem` — TypeScript-тип,
приводящий разные сущности к единому виду для UI. Он не хранится в БД.

**Известный тех. долг (зафиксирован, не узаконен):**
`Doctor.region` + `regionId`, `Clinic.region` + `regionId`, `Clinic.phone` + `phones`,
`Clinic.specializationTags` при наличии `ClinicOnSpecialty`. Источник истины —
реляционное поле; строковые поля legacy. Новых таких дублей вводить нельзя.

## 5. Все связи должны быть достоверными

**Главный принцип проекта.** Энциклопедия существует ради доверия; ложная связь
разрушает его сильнее, чем отсутствие данных.

**Правила:**
1. Нет достоверного источника — **связи нет**.
2. Нет данных — **поле пустое**. Не придумывать, не додумывать, не заполнять «похожим».
3. Технические данные — из документации производителя, не из маркетинга.
4. При расхождении источников — брать пересечение, расхождение отражать текстом.
5. Пустой раздел **лучше** правдоподобной выдумки.

**Реальные примеры соблюдения:**
- `Equipment.year` у ZEISS VisuMax 800 пуст — год выпуска не подтверждён ни брошюрой,
  ни сайтом производителя.
- Врач Дубровина не связана с VisuMax 800: сайт клиники указывает владение SMILE Pro,
  но платформа явно закреплена за другим хирургом. Однозначного подтверждения нет —
  связи нет.
- Процедура `smile` (классический) не связана с VisuMax 800: в официальной таблице
  вмешательств указан только `SMILE pro`.

## 6. Транзитивные связи — только если логически корректны

Транзитивная связь `A → B → C` допустима, **только если утверждение «A связано с C»
истинно по построению**.

### ✅ Корректно

| Связь | Утверждение | Почему истинно |
|---|---|---|
| `ScientificWork → Clinics` через автора | «Клиники автора работы» | Автор действительно там работает |
| `Clinic → ScientificWorks` через врачей | «Работы врачей этой клиники» | Врачи действительно там работают |

Обе подписаны на UI так, чтобы природа связи была явной.

### ❌ Некорректно

| Связь | Почему нельзя |
|---|---|
| `ScientificWork → Diseases` через врача | «Направления врача» ≠ «тема работы» |
| `ScientificWork → Procedures` через врача | То же |

**Реальный дефект, из которого выведено правило:**

| | Значение |
|---|---|
| Тема диссертации | «Экспресс кросслинкинг при кератэктазиях» |
| Направления автора | Косоглазие, Катаракта, Птоз |

Транзитивный вывод дал бы диссертацию про кросслинкинг на странице «Катаракта» и
«Птоз» — медицинскую дезинформацию. Поэтому созданы прямые связи
`ScientificWorkOnDisease` / `ScientificWorkOnProcedure`.

**Проверка перед использованием транзитивности:**
сформулируйте связь словами. Если формулировка требует оговорки («ну, вообще-то это
значит немного другое») — связь недопустима.

## 7. Любая новая сущность встраивается в граф

Новая сущность обязана иметь:
1. `slug` + собственную страницу;
2. хотя бы одну **двустороннюю** связь с существующими сущностями;
3. запись в [`graph-model.md`](./graph-model.md) с указанием типа каждой связи;
4. правила наполнения (что достоверно, что оставлять пустым).

## 8. Расширение предпочтительнее создания нового

Прежде чем заводить сущность или поле — проверьте, решается ли задача **данными**
в существующей модели.

**Иерархия решений (от лучшего к худшему):**
1. Добавить **данные** в существующую модель. ← по умолчанию
2. Добавить **связь** между существующими сущностями.
3. Добавить **аддитивное** поле (nullable) / новую join-таблицу.
4. Создать новую сущность — только если предметная область действительно другая.
5. Изменить существующее поле — **только через архитектурное решение**.

**Пример №1 (расширение):** 8 разнотипных аппаратов (лазеры, ОКТ, биометры,
микроскопы, витреосистемы) добавляются **только данными** — благодаря
`EquipmentCategory` + `EquipmentSpec`. Схема не меняется.

**Пример №2 (обоснованно новая сущность):** исследования конкретного аппарата — это
**не** `ScientificWork` (у той владелец — врач). Для этого создаётся `ClinicalStudy`,
а не расширяется чужая по смыслу модель.

## 9. Аддитивность изменений схемы

Если изменение схемы всё же обосновано, оно должно быть **аддитивным**.

**Разрешено:** `ADD COLUMN` (nullable), `CREATE TABLE`, `CREATE INDEX`,
`ADD CONSTRAINT` на новых таблицах.

**Запрещено:** `DROP`, `TRUNCATE`, `RENAME`, `ALTER COLUMN`, `DELETE FROM`.

**Обязательный порядок:**
1. `prisma migrate diff --from-config-datasource --to-schema … --script` — получить SQL.
2. Проверить на деструктивные операции.
3. Применить (при необходимости — через `prisma db execute`, не подавляя
   предупреждения флагами вслепую).
4. Прогнать seed **дважды** — счётчики не должны меняться.

**Идемпотентность seed обязательна.** Обеспечивается составными PK join-таблиц
(`@@id([aId, bId])`) и `upsert` по уникальным ключам.

## 10. Достоверность превыше полноты

Сводное правило, из которого следуют все предыдущие.

> Незаполненное поле — честно. Выдуманное — ложь.
> Отсутствующая связь — незавершённость. Ложная связь — дезинформация.

При конфликте «сделать быстрее» и «сделать достоверно» — выигрывает достоверность.
Если данных не хватает — это сообщается, а не заполняется правдоподобным.
