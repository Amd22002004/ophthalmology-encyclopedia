# План переноса документации в GitHub Wiki

> Статус: **план, не выполнен.** Документ описывает, что имеет смысл перенести в Wiki,
> а что должно остаться в репозитории — и почему.

## Главный принцип разделения

| Критерий | Репозиторий (`docs/`, `.github/`) | GitHub Wiki |
|---|---|---|
| **Версионируется вместе с кодом?** | Да — обязана | Нет — живёт отдельно |
| **Меняется при изменении кода?** | Да | Редко |
| **Проверяется в code review?** | Да, в том же PR | Нет |
| **Тип** | Контракт, источник истины | Онбординг, справка, инструкции |

> **Правило:** если документ должен меняться **в том же PR**, что и код, — он остаётся
> в репозитории. Wiki не проходит code review и легко разъезжается с реальностью.

Для архитектуры это критично: `graph-model.md` описывает контракт. Его расхождение с
`schema.prisma` = потеря источника истины. В Wiki такое расхождение никто не заметит.

| `docs/architecture/publications.md` | Описывает инварианты `ScientificWork` / `Publication` |
| `docs/architecture/doctors.md`, `clinics.md`, `diseases.md`, `procedures.md` | Привязаны к полям схемы |
| `docs/architecture/CHANGELOG.md` | Журнал решений, версионируется |
| `docs/architecture/ROADMAP.md` | Содержит фактические цифры наполнения |

| `README.md` | Витрина репозитория |

**Вся текущая документация остаётся в репозитории.** Ни один существующий документ
переносить не следует.

## ✅ Что имеет смысл создать в Wiki (новые материалы)

Wiki полезна для того, чего сейчас **нет** и что не является контрактом.

### 1. Onboarding: «Первый день в проекте»
Пошагово: клонирование → `.env` → PostgreSQL (Docker) → `db push` → `db:seed` → `dev`.
Со скриншотами и типичными ошибками.
**Почему Wiki:** длинно, со скриншотами, не влияет на код.

### 2. Runbook: развёртывание и эксплуатация
Регламент деплоя (bundle → scp → fetch → build → PM2), проверка `migrate diff`,
откат, чтение логов PM2.
**Почему Wiki:** операционная инструкция; содержит инфраструктурные детали, которым
не место в публичном репозитории.
⚠️ **Реквизиты серверов — только в Wiki приватного репозитория или в менеджере секретов.**

### 3. Гайд по наполнению для редактора
Как добавить врача / оборудование / научную работу: где брать источники, что делать
при их расхождении, как готовить фото и PDF, требования к слагам.
**Почему Wiki:** аудитория — редакторы, а не разработчики.

### 4. FAQ по архитектурным решениям
«Почему нельзя связать работу с заболеваниями через врача?»,
«Почему `Equipment` заморожена?», «Почему `slug` у `ScientificWork` nullable?».
**Почему Wiki:** развёрнутые пояснения; в самих документах — только краткая суть.

### 5. Глоссарий
Кератэктазия, кросслинкинг, SMILE Pro, ВАК, ОМС, лентикула…
**Почему Wiki:** справочник, не связан с кодом.

### 6. Каталог источников
Реестр использованных источников: брошюры производителей, сайты клиник, авторефераты —
с датами обращения.
**Почему Wiki:** растёт постоянно, полезен редакторам.

## Обязательное правило связывания

Чтобы Wiki не стала вторым источником истины:

1. **Home Wiki** начинается с блока:
   > Архитектура проекта описана в репозитории: `docs/architecture/`.
   > Wiki содержит только онбординг, инструкции и справочники.
   > **При расхождении верен репозиторий.**

2. **Никогда не копировать** в Wiki содержимое `docs/architecture/` — только ссылки.
   Копия устареет и начнёт врать.

3. Wiki **не может** переопределять архитектурные правила.

## Когда переносить

Не сейчас. Wiki имеет смысл, когда появится **вторая аудитория**:

- подключились разработчики, которым нужен онбординг;
- появились редакторы-неразработчики;
- деплой выполняет не автор проекта.

Пока проект ведёт один человек с AI-ассистентом, вся документация в репозитории —
это преимущество: она рядом с кодом, версионируется и проверяется в review.

**Приоритет при старте Wiki:** Runbook (деплой) → Onboarding → Гайд по наполнению.
